# 0008. Alerts: materialized alert rows from threshold rules

- Status: accepted

## Context

The client nav tree includes ALERTS > Active Alerts + Alert Rules. Inventory needs proactive
warning (low stock, near expiry, QC backlog) rather than a human re-reading dashboards daily.
Not decided here: notification channels (email/SMS) — deferred.

## Decision Drivers

- Alerts must be visible without recomputing the whole inventory on every page load.
- Dismissal/acknowledgement must persist, so alerts cannot be purely computed views.
- Demo environment: no external message broker; must run on the Quarkus dev server alone.

## Considered Options

1. **Pure computed views** (query on read) — always consistent, but no place to persist dismissal; rejected.
2. **Materialized `alert` rows** generated by a `@Scheduled` evaluator from `alert_rule` thresholds — dismiss/resolve persist; slight staleness (minutes) acceptable; chosen.
3. External rule engine / message queue — YAGNI (§3.2); no infra in the demo environment.

## Decision

Option 2. `alert_rule(rule_type [LOW_STOCK|NEAR_EXPIRY|QC_OVERDUE], scope_ref, threshold, active)`
drives a scheduled `AlertEvaluator` that upserts open `alert` rows; alerts resolve when the
condition clears. AI-drafted; accepted by the project owner.

## Consequences

Easier: dismiss/resolve UX, auditability of what fired when. Harder: staleness window exists
(mitigated by an on-demand regenerate endpoint). Deferred: channels, escalation, per-user
subscriptions.
