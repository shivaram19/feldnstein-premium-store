# 0015. Commerce review defect fixes (stock atomicity, payment integrity, pricing guardrails)

- Status: accepted

## Context

An expert e-commerce review of the Quarkus backend found ten concrete defects in
the commerce code: the stock allocator silently under-reserves, two hot
aggregates (StockLevel, CustomerOrder) have no optimistic locking, a payment
arriving after cancellation orphans captured money, stock adjustments can push
on-hand below reserved, expired-cart cleanup runs outside a transaction,
unpriced variants check out at ₹0, order numbers carry only a 2-digit entropy
suffix, the payment-verify double-submit loses to its own race, payment.order_id
has no uniqueness guarantee, and the storefront catalog query disagrees with the
charging query on which PriceConfig wins. This record covers the decision to fix
them as a batch; the defect list itself came from the human review, not from AI
exploration.

## Decision Drivers

- Money and stock correctness dominate: silent under-reservation and orphaned
  captures corrupt ledger state that is hard to repair after the fact.
- Checkout failures must abort the whole transaction (§3.8: evidence of
  correctness over presumptive tolerance).
- Migrations must stay valid on both PostgreSQL (prod) and H2 (dev/test).
- The fix list is bounded; the review explicitly deferred partial refunds,
  webhooks, in-transaction gateway HTTP, shipping charges, and pagination.

## Considered Options

1. Apply the ten fixes exactly as prescribed by the review — smallest correct
   change per defect, TDD tests beside each one. Risk: touches checkout, payment
   and inventory paths at once.
2. Redesign the checkout/payment flow (saga, outbox, idempotency keys) —
   addresses root causes but is a much larger one-way door than the evidence
   justifies right now.
3. Do nothing — ₹0 orders, orphaned captures and silent under-reservation keep
   shipping to real customers.
N. Defer the riskiest subset — the review already did this; what remains is the
   minimal safe set.

## Decision

Option 1. Each fix follows the review's prescription: fail closed with a
DomainException where silent partial success was possible, add `@Version`
optimistic locking to StockLevel and CustomerOrder, route post-cancellation
payments into the existing refund path, make expired-cart deletion
transactional, reject adjustments below reserved, require a selling price (MRP
fallback stays), widen the order-code suffix to 6 digits, treat the
already-paid verify race as idempotent success, constrain payment.order_id
uniquely in V11, and order the storefront price query by effectiveFrom desc.
Implementation code and tests were generated by an AI agent (Kimi Code) from the
human-authored fix list; the repository maintainer remains the accountable
owner. Options were not AI-generated — they are the review's enumeration.

## Consequences

Checkout can now fail at reservation time with a rollback instead of shipping
under-allocated orders; concurrent checkouts on the same stock hit optimistic
locking; double payment-verify returns success instead of a 400. The V11
constraint makes duplicate payments impossible at the database level, so the
retry paths that call `initiate` when no payment is found fail loudly rather
than duplicating. Two-way door: all changes are code-level and reversible, and
the migration is additive-only. Out of scope (per the review): a global
DomainException→4xx exception mapper does not exist yet, so the new
DomainException rejections surface as 500s at the REST layer until one is added.
